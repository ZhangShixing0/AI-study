# AI 督学服务器容量与扩展架构备忘

本文档记录 MVP 内测、早期正式上线、上万注册用户阶段的服务器选择、容量估算、降压设计和后续扩展路线。

## 1. 当前项目功能回顾

当前 AI 督学 MVP 主要功能：

- 测试码进入内测空间。
- 新用户首次建档：目标分数、A/B/C/D 班型、核心习题册、备选习题册。
- 按班型和学生进度生成每日计划。
- 每日计划精确到具体题目编号，例如《1000》第二章基础：5、6 题。
- 用户提交每日做题状态：正确、错误、未做。
- 第二天根据个人进度和反馈继续更新计划。
- 展示学习曲线、排行榜、自习室、专注记录等辅助页面。
- 当前技术形态：FastAPI + SQLite + 静态前端原型。

## 2. 核心压力判断

这个项目不应该按“高实时 AI 计算系统”来估算，而更接近“学习计划分发 + 低频状态写入系统”。

原因：

- 每日计划生成规则较简单：班型决定题型顺序，学生只是在固定顺序上的进度指针不同。
- 题型确定后，再按班型、习题册、阶段从题库中取具体题目。
- 不需要每个用户打开页面时都实时进行复杂 AI 计算。
- 排行榜、曲线、自习室都可以降低刷新频率。

真正的压力主要来自：

- 同时打开页面时的静态资源和接口请求。
- 晚上集中提交状态时的写入。
- 早上集中读取今日计划。
- 数据库从 SQLite 逐步增长后的写入锁和查询性能。
- 带宽不足导致页面加载慢。

## 3. 已确认的降压设计

### 3.1 每日计划夜间预生成

推荐流程：

```text
用户当天提交状态
→ 写入反馈和进度
→ 夜间批处理生成明日计划
→ 第二天用户打开页面时直接读取已生成计划
```

这样可以避免大量用户早上同时打开页面时才实时生成计划。

### 3.2 计划生成不依赖重 AI

A/B/C/D 班型的题型顺序固定：

```text
班型 → 当前进度指针 → 题型 → 班型可用题目 → 今日计划
```

每个学生只是进度指针不同，例如：

- 学生 A：第二章题型一。
- 学生 B：第四章题型二。
- 学生 C：第一章未完成题补做。

因此计划生成可以主要由程序规则完成，AI 只做文案、解释或策略微调。

### 3.3 排行榜和曲线夜间更新

排行榜、曲线、掌握度统计可以每天晚上批量计算并落表。

用户白天访问时只读取预计算结果：

```text
student_stats
type_mastery_stats
loss_reason_stats
priority_recommendations
```

这样不需要每次访问都重新聚合大量历史数据。

### 3.4 今日打卡榜可替换为低频榜单

如果今日实时打卡榜造成写入和排序压力，可以先替换为：

- 昨日完成榜。
- 本周坚持榜。
- 连续学习天数榜。
- 班级进度榜。

这些都适合夜间批量更新。

### 3.5 自习室低频刷新

自习室不需要秒级实时。

建议：

```text
每 30 分钟刷新一次同桌/陪伴状态
```

早期甚至可以只展示“同班最近在线/最近学习”用户，不做实时在线系统。

## 4. 服务器规格与用户规模估算

以下估算基于：

- FastAPI 单机部署。
- SQLite 或早期 PostgreSQL。
- Nginx 反向代理。
- 静态资源尽量压缩，后续可接 CDN。
- 每日计划夜间预生成。
- 排行榜、曲线夜间批处理。
- 自习室低频刷新。

这些数字是工程估算，不是云厂商承诺值。

| 服务器规格 | 适合阶段 | 可承载注册用户 | 日活用户 | 同时在线用户 | 同时高频操作用户 |
|---|---|---:|---:|---:|---:|
| 2核2G / 3-4Mbps | MVP 内测 | 1,000-5,000 | 200-800 | 50-150 | 10-30 |
| 2核4G / 100GB / 7Mbps | 内测 + 早期上线 | 5,000-20,000 | 1,000-3,000 | 200-800 | 30-100 |
| 4核8G / 100-180GB / 10-12Mbps | 更稳的正式上线起步 | 20,000-50,000 | 3,000-10,000 | 800-2,000 | 100-300 |
| 8核16G / 更高带宽 | 增长期单机上限探索 | 50,000+ | 10,000+ | 2,000-5,000 | 300-800 |

说明：

- “注册用户”只是数据库里有多少用户，不等于服务器实时压力。
- “日活用户”决定一天内读写总量。
- “同时在线用户”决定页面访问和静态资源压力。
- “同时高频操作用户”决定后端接口和数据库写入压力。

## 5. 关于 2核4G / 100GB / 7Mbps 的结论

这个配置可以作为第一年启动服务器，但不能作为万人同时在线的最终单机方案。

适合它承载的场景：

```text
几千到一两万注册用户
每天一两千人使用
同时在线几百人
计划和统计都已预生成
静态资源不太大
没有大量实时写入
```

不适合它承载的场景：

```text
10,000 人同一时间在线
晚上大量用户同一秒提交状态
早上大量用户同一秒请求生成计划
静态图片全部从本机 7Mbps 带宽发送
SQLite 长期承接大量并发写入
```

如果预算敏感，可以买 2核4G 年付，用于 MVP、内测和早期正式上线。

如果希望第一年更稳，建议直接买 4核8G。

## 6. 推荐购买策略

### 6.1 预算敏感策略

```text
购买：2核4G / 100GB / 7Mbps
周期：年付可接受
定位：MVP 内测 + 早期上线
数据库：先 SQLite，后迁 PostgreSQL
```

优点：

- 成本低。
- 足够支持当前 MVP 和早期用户。
- 部署简单。

风险：

- 流量增长后需要迁移。
- 7Mbps 带宽可能比 CPU 更早成为瓶颈。
- SQLite 需要尽早规划迁移。

### 6.2 稳妥启动策略

```text
购买：4核8G / 100-180GB / 10-12Mbps
周期：年付更合适
定位：早期正式上线服务器
数据库：可以先 SQLite，但建议更早迁 PostgreSQL
```

优点：

- 对早期正式上线更从容。
- 可承载更多日活和同时在线。
- 给后续批处理、日志、监控留出余量。

风险：

- 成本更高。
- 仍然不是万人同时在线的最终架构。

### 6.3 不建议的策略

不建议为了“年付便宜”直接把单台 2核4G 当成最终生产架构。

服务器可以买一年，但架构要允许后续迁移：

- 数据库从 SQLite 迁 PostgreSQL。
- 静态资源接 CDN。
- 后端从单实例变多实例。
- 夜间任务从进程内脚本变成独立任务队列。

## 7. 上万注册用户后的推荐架构

当注册用户接近或超过 10,000，并且日活明显增长时，建议演进为：

```text
CDN
  ↓
Nginx / 负载均衡
  ↓
FastAPI 应用服务器 1
FastAPI 应用服务器 2
FastAPI 应用服务器 3
  ↓
PostgreSQL 主数据库
Redis 缓存 / 限流 / 任务状态
  ↓
夜间批处理任务 / 队列 Worker
  ↓
对象存储 / 数据库备份 / 日志监控
```

### 7.1 CDN

用途：

- 承载前端静态资源。
- 承载图片、图标、较大的静态文件。
- 减少服务器带宽压力。

优先级：正式上线前后尽早接入。

### 7.2 PostgreSQL

SQLite 适合 MVP，但上万注册用户后建议迁移到 PostgreSQL。

迁移原因：

- 更适合并发写入。
- 更适合复杂查询和索引优化。
- 更适合长期正式数据。
- 后续可以扩展全文检索、统计分析、向量能力等。

### 7.3 Redis

用途：

- 缓存排行榜、曲线、班级统计。
- 缓存测试码/登录状态。
- 做接口限流。
- 保存夜间任务状态。

### 7.4 多台 FastAPI 应用服务器

当单台服务器 CPU、内存或连接数接近瓶颈时，把 FastAPI 拆成多实例：

```text
应用服务器 A
应用服务器 B
应用服务器 C
```

前面用 Nginx 或云负载均衡分发请求。

### 7.5 夜间批处理任务

独立任务负责：

- 生成明日计划。
- 计算排行榜。
- 计算学习曲线。
- 更新掌握度。
- 生成班级/用户统计。

早期可以用 cron：

```text
每天 02:00 生成明日计划
每天 03:00 更新统计数据
每天 03:30 备份数据库
```

后期再升级为 Celery/RQ/云任务队列。

## 8. 功能设计上的长期降压原则

### 8.1 能预生成的不要实时生成

适合预生成：

- 明日计划。
- 排行榜。
- 曲线。
- 掌握度。
- 推荐优先级。

### 8.2 能读缓存的不要实时聚合

用户打开页面时，尽量读取已经算好的结果。

避免每次访问都：

- 扫历史反馈。
- 重新计算排名。
- 重新统计章节掌握度。

### 8.3 能低频刷新的不要高频刷新

自习室、陪伴状态、榜单可以低频刷新。

推荐：

```text
自习室：30 分钟刷新一次
排行榜：每日更新
曲线：每日更新
学习统计：每日更新
```

### 8.4 写操作要尽量少而明确

高价值写入：

- 提交今日题目状态。
- 更新进度指针。
- 保存计划。
- 记录关键学习行为。

低价值写入要谨慎，例如：

- 鼠标/页面停留。
- 频繁在线心跳。
- 秒级自习室状态。

## 9. 阶段路线图

### 阶段 1：MVP 内测

```text
单台 2核4G
FastAPI
SQLite
测试码
手动/脚本备份
```

目标：

- 验证每日计划是否合理。
- 验证用户是否愿意每日反馈。
- 验证第二天计划是否有持续督学感。

### 阶段 2：早期上线

```text
2核4G 或 4核8G
Nginx
systemd
SQLite 或 PostgreSQL
CDN 可选
夜间批处理脚本
```

触发升级信号：

- 日活超过 1,000。
- 晚上提交反馈变慢。
- 早上打开计划变慢。
- 数据库文件增长明显。

### 阶段 3：上万注册用户

```text
4核8G 起步
PostgreSQL
Redis
CDN
夜间批处理
数据库备份
基础监控
```

触发升级信号：

- 注册用户超过 10,000。
- 日活超过 3,000。
- 同时在线超过 800。
- SQLite 写入锁或响应慢开始出现。

### 阶段 4：万人同时在线目标

```text
负载均衡
多台 FastAPI
PostgreSQL 独立数据库
Redis
CDN
对象存储
任务队列
监控告警
灰度发布
```

这个阶段不再依赖单台轻量服务器。

## 10. 当前建议

如果现在准备购买服务器：

预算敏感：

```text
2核4G / 100GB / 7Mbps
可以买一年
用于内测和早期上线
```

更稳妥：

```text
4核8G / 100-180GB / 10-12Mbps
更适合第一年认真上线
```

无论选择哪个，都建议坚持：

- 计划夜间预生成。
- 统计夜间批量更新。
- 自习室低频刷新。
- 服务器开始真实内测后不要随便重置 `backend/app.db`。
- 用户增长后优先迁 PostgreSQL 和接 CDN。
